Nano SEO Lab

What Nano SEO Lab is for

A practical page-level SEO lab that combines normal browser checks with small, focused model reviews where context is useful.

Start here: analysing a page

For a normal page review, the shortest path is: choose who reviews the page → Run analysis → start with Prioritised actions. Run analysis reads the current page first, so you do not need to click Read page separately unless you only want the browser checks and page evidence.

Nano SEO Lab separates the work into three layers:

  • Page evidence is what the browser and deterministic checks can establish directly.
  • Model review interprets evidence where context matters.
  • Actions are the subset of results that may be worth doing something about.
  1. Open the page you want to inspect and click the Nano SEO Lab extension icon. This gives the extension temporary access to that tab and opens the side panel.
  2. Choose who reviews the page. Nano can run locally in Chrome where available, or you can use a configured Gemini or OpenAI model.
  3. Click Run analysis for the normal full-page workflow. It reads the page, runs the configured checks and combines the results.
  4. Start with Prioritised actions, then open Findings or the specialist tabs when you need the underlying evidence.
  5. Use Read page when you only want to refresh the deterministic page evidence without running the full model-assisted workflow.

If you switch to another tab or site, click the extension icon on that page before analysing it. Nano SEO Lab uses temporary page access rather than permanent access to every website.

What the main checks are doing

Deterministic SEO checks cover things a browser can establish directly, such as metadata, headings, canonicals, robots directives, links, images, hreflang and structured-data signals. These do not need a language model to decide whether the underlying fact exists.

Finding review keeps the factual finding separate from the model judgement. A finding is the condition detected by the browser checks. Model review then decides whether the detector itself appears wrong, whether the real condition has little or no material impact, whether impact depends on context, or whether it looks meaningful. The interface uses Likely detector error only when the detector appears factually wrong; a real-but-benign condition is shown as a real condition with low or no material impact.

Site check exclusions can be configured in Settings for exact hostnames or wildcard subdomains. Use these for known, non-actionable platform constraints. Excluded checks remain visible for traceability but are removed from issue triage, model review and prioritised actions for matching hosts.

Model review is used where the answer is more contextual: what role a link appears to play, what type of page this is, the likely user intent, whether page type and intent align, whether a flagged issue may be a false positive, and whether server/rendered differences look meaningful.

Server vs rendered comparison helps surface content or links that change after JavaScript runs. This is useful when considering what different crawling or retrieval pipelines may encounter. Iframe elements themselves can appear in this comparison, but the document rendered inside an iframe is treated separately rather than silently merged into the parent DOM.

Iframe content advisory reports visible iframes and, where the browser can read the embedded document, summarises the number of words, headings and links inside them. This is a caution rather than an automatic error: iframe content can be indexed or attributed differently from ordinary parent-page content. Cross-origin or otherwise inaccessible frames are reported as unknown rather than guessed. If an embedded document uses noindex,indexifembedded, the extension calls that out separately because Google may index that content when it is embedded, even though the iframe URL itself is noindex. That behaviour is Google-specific and should not be assumed for other search engines or AI retrieval systems.

URL and locale review brings canonical, hreflang and related identity signals together so contradictions are easier to spot.

Indexability signal checking is deliberately manual because it makes extra network requests. When requested, it compares the current HTTP response, server HTML, rendered DOM, robots.txt and canonical target for conflicting canonical or robots signals. It also evaluates the current URL against known AI/search crawler controls and checks the source <head> for markup that may force the parser out of head mode, showing which later metadata may be displaced.

Link response checking is also manual. When requested, it follows HTTP(S) destinations and records their final responses. These network checks may ask for temporary permission to access the required origins.

Optional: use it as a model-testing framework

You do not need to compare models to use Nano SEO Lab. The comparison features are there for testing how different models and page representations affect the same SEO judgement.

For a simple comparison, select two or more providers and run the same task. Most tasks use closely related evidence and judgement labels across providers, but the output shape is not always identical. The interface labels these as reviews or summaries according to the role they are performing rather than pretending every provider is returning the same thing.

Nano vs Gemini/OpenAI: Nano is primarily a local summarisation, classification and triage layer. It is useful for compact tasks where the extension can pre-compile the evidence and ask the model for a bounded answer. In DOM review specifically, Nano summarises the supplied deterministic evidence rather than acting as the final rich judgement layer. Gemini and OpenAI receive the fuller review task and can return more detailed structured judgements, rationales and per-item assessments. This means a Nano result should not be expected to have exactly the same fields or level of explanation as a Gemini/OpenAI result.

For page type and intent, you can also change the evidence representation sent to the model:

  • Structured digest is the normal starting point: compact, preprocessed evidence.
  • Clean HTML retains useful markup while removing some implementation noise.
  • Clean Markdown emphasises page content and structure.
  • Visible page text removes markup and tests the text alone.
  • Rendered HTML provides the largest and noisiest representation.
  • Compare all five runs the task against each representation so you can see whether the input format changes the result.

Use Analysis history and the Model call log when you need to inspect or export the underlying runs. Reusing saved model results is useful for ordinary work; turn it off when you specifically want a fresh comparison.

Why use Nano?

The main attraction of Chrome's Nano model is that, where the browser supports it, inference can happen locally rather than requiring every page review to be sent to an external model API. In the current workflow Nano is best thought of as a lightweight local reviewer: it handles compact classification, summarisation and triage tasks after the extension has already done the deterministic evidence gathering.

There are trade-offs. Nano is a smaller model with tighter context and output constraints, so the extension now gives it narrower tasks rather than trying to force parity with hosted models. For example, DOM review uses Nano to summarise compiled evidence, while Gemini and OpenAI perform the fuller structured judgement. Nano therefore tends to produce shorter, more bounded outputs; Gemini/OpenAI can provide richer rationales and item-level assessments. Browser and device support can also affect Nano availability.

For that reason, Nano SEO Lab does not treat a model answer as ground truth. Deterministic checks remain deterministic, model judgements retain their evidence, and the comparison tools make disagreement visible.

Data and privacy

Page snapshots, analysis history, model-call logs and cached model results are stored locally in Chrome. They are not sent to a Nano SEO Lab developer-operated analytics service.

Chrome Nano stays local to Chrome. If you choose Gemini or OpenAI, only the evidence needed for that review task is sent directly from your browser to the selected provider using your own API key.

Gemini and OpenAI API keys are stored locally in Chrome. They are kept in local extension storage so you do not need to re-enter them each time Chrome starts. They are sent only to the selected API provider when that provider is used.

Use Settings → Clear saved model results to clear the model cache, or Clear all local analysis data to remove saved page snapshots, analysis history, model-call logs and cached results.

Security and untrusted page content

A webpage is data, but it can contain text that looks like an instruction to an AI model. This creates a prompt-injection risk when page content is passed into model-powered analysis.

Nano SEO Lab uses several layers of defence:

  • Page content is explicitly treated as untrusted evidence. It is separated from the trusted task instructions before being sent to a model. Previous model outputs used by another task are treated as untrusted too.
  • Potential instruction-like content is flagged. A local scanner looks for patterns such as attempts to override instructions, impersonate system prompts or request secrets. A warning is shown, but the evidence is not silently removed or rewritten.
  • Model outputs are validated. Responses must match the expected structure, and tasks that operate on supplied IDs must return the expected IDs. Invalid output is logged and rejected rather than quietly fed into later analysis.
  • There is no automatic security retry or sanitisation step. This keeps the original evidence and model behaviour inspectable instead of creating an invisible second version of the page.

These controls reduce risk; they do not make arbitrary webpage content inherently trustworthy. A prompt-injection warning is also not proof that a page is malicious. Legitimate articles can discuss prompts, instructions and security attacks too.

A sensible way to interpret the results

Use findings as factual page evidence. Treat model reviews as contextual judgements that can help prioritise or explain that evidence, not as replacements for the underlying facts.

For day-to-day work, start with Prioritised actions. Open Finding details when you want to separate what the browser found from what the model thought it meant. For research, comparison or debugging, inspect individual model outputs, evidence representations and history instead.
