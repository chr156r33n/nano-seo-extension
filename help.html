Start here: analysing a page

Nano SEO Lab is designed to sit between a traditional SEO extension and a model-powered review. It collects evidence from the page, runs deterministic checks where a rule can be tested directly, and uses a selected model for the parts that benefit from interpretation.

  1. Open the page you want to inspect and click the Nano SEO Lab extension icon. This gives the extension temporary access to that tab and opens the side panel.
  2. REQUIRED (first time) Choose who reviews the page. Nano can run locally in Chrome where available, or you can use a configured Gemini or OpenAI model.
  3. REQUIRED Click Read this page. This captures the current rendered page and the deterministic SEO evidence used by the checks.
  4. OPTIONAL Click Run analysis (takes longer). The selected checks run together and produce a prioritised action summary, supporting results and the checks the page passed.
  5. OR Drill into individual tools/checks. You can classify links, compare page type with intent, compare server HTML with the rendered DOM, review URL and locale signals, or manually check link responses.

If you switch to another tab or site, click the extension icon on that page before analysing it. Nano SEO Lab uses temporary page access rather than permanent access to every website.

What the main checks are doing

Deterministic SEO checks cover things a browser can establish directly, such as metadata, headings, canonicals, robots directives, links, images, hreflang and structured-data signals. These do not need a language model to decide whether the underlying fact exists.

Model review is used where the answer is more contextual: what role a link appears to play, what type of page this is, the likely user intent, whether page type and intent align, whether a flagged issue may be a false positive, and whether server/rendered differences look meaningful.

Server vs rendered comparison helps surface content or links that change after JavaScript runs. This is useful when considering what different crawling or retrieval pipelines may encounter.

URL and locale review brings canonical, hreflang and related identity signals together so contradictions are easier to spot.

Indexability signal checking is deliberately manual because it makes extra network requests. When requested, it compares the current HTTP response, server HTML, rendered DOM, robots.txt and canonical target for conflicting canonical or robots signals.

Link response checking is also manual. When requested, it follows HTTP(S) destinations and records their final responses. These network checks may ask for temporary permission to access the required origins.

Optional: use it as a model-testing framework

You do not need to compare models to use Nano SEO Lab. The comparison features are there for testing how different models and page representations affect the same SEO judgement.

For a simple comparison, select two or more providers and run the same task. The extension gives each selected model the same task prompt and output structure, which makes disagreement easier to inspect rather than hiding it behind differently shaped responses.

For page type and intent, you can also change the evidence representation sent to the model:

  • Structured digest is the normal starting point: compact, preprocessed evidence.
  • Clean HTML retains useful markup while removing some implementation noise.
  • Clean Markdown emphasises page content and structure.
  • Visible page text removes markup and tests the text alone.
  • Rendered HTML provides the largest and noisiest representation.
  • Compare all five runs the task against each representation so you can see whether the input format changes the result.

Use Analysis history and the Model call log when you need to inspect or export the underlying runs. Reusing saved model results is useful for ordinary work; turn it off when you specifically want a fresh comparison.

Why use Nano?

The main attraction of Chrome's Nano model is that, where the browser supports it, model inference can happen locally rather than requiring every page review to be sent to an external model API. That makes it useful for lightweight, repeatable classification and for experimenting with on-device AI as part of an SEO workflow.

There are trade-offs. Nano is a smaller model, so complex judgements can be less reliable than larger hosted models. It also has tighter practical batch limits, which is why the extension recommends smaller link and DOM-review batches for Nano. Browser and device support can also affect availability.

For that reason, Nano SEO Lab does not treat a model answer as ground truth. Deterministic checks remain deterministic, model judgements retain their evidence, and the comparison tools make disagreement visible.

Security and untrusted page content

A webpage is data, but it can contain text that looks like an instruction to an AI model. This creates a prompt-injection risk when page content is passed into model-powered analysis.

Nano SEO Lab uses several layers of defence:

  • Page content is explicitly treated as untrusted evidence. It is separated from the trusted task instructions before being sent to a model. Previous model outputs used by another task are treated as untrusted too.
  • Potential instruction-like content is flagged. A local scanner looks for patterns such as attempts to override instructions, impersonate system prompts or request secrets. A warning is shown, but the evidence is not silently removed or rewritten.
  • Model outputs are validated. Responses must match the expected structure, and tasks that operate on supplied IDs must return the expected IDs. Invalid output is logged and rejected rather than quietly fed into later analysis.
  • There is no automatic security retry or sanitisation step. This keeps the original evidence and model behaviour inspectable instead of creating an invisible second version of the page.

These controls reduce risk; they do not make arbitrary webpage content inherently trustworthy. A prompt-injection warning is also not proof that a page is malicious. Legitimate articles can discuss prompts, instructions and security attacks too.

A sensible way to interpret the results

Use deterministic findings as factual page evidence. Treat model results as contextual judgements that can help prioritise or explain that evidence, not as an oracle with unusually strong opinions about title tags.

For day-to-day work, the prioritised action summary is the quickest route through the results. For research, comparison or debugging, inspect individual model outputs, evidence representations and history instead.
